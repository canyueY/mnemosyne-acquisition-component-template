# 新来源开发指南

## 先选最小获取方式

优先检查现有组件是否覆盖。新需求可从用户导出文件、获授权的官方 API、明确配置的 Webhook、用户提供的公开页面或其他授权输入开始。不要默认选择“登录整个账号并全量抓取”。

每种方式都要说明：谁提供数据、能看见多少、不能看见什么、如何增量、如何停止和撤回，以及失败时是否可能已经产生外部作用。

模板不提供读取本地文件、剪贴板、网络请求或浏览器自动化的实现；这些都由衍生项目按需求开发。

## 来源档案的最小字段

- source_id / source_name / access_method。
- 允许的账号/会话/频道/目录/公开页面范围；与实际授权记录的引用。
- 原平台 record_id、修订、分页 cursor、时间精度及稳定 URI/位置。
- snapshot_scope 与 completeness；缺失模态和缺失时间段。
- 记录是作者发言、用户自述、工具观察还是衍生摘要。
- 允许存储/转发/训练、保留期限和删除处理；由谁实际执行这些策略。
- 默认只采集、可选哪些进一步能力、这些能力是否已实现。

SourceIdentity.root_source_id 是可追溯声明，不是自证真实身份或独立证据。认证与独立性仍需 Node 的授权和验证规则。

## 假设示例：新的聊天来源

用户明确提供某段导出记录：逐条保留发言者、消息主键、会话范围与时间。其他人的发言为 author_claim，不可批量标为当前用户偏好；引用/转发保留原来源，不多算支持。

仅导入选中时间段时，completeness=partial。没有出现在这段导出里的旧消息不能自动撤回。附件未导出时记录缺失，不假装分析过附件内容。

## 假设示例：新的内容平台

只得到标题/简介时不能生成“已观看完整内容”；字幕可支持文本发言记录，不能支持画面内容。评论、作者观点、视频内容和 Agent 解释分别标记。

源页面修订后新增 revision，并让依赖旧版本的摘要/索引/候选认识接受 Node 的重审；不要覆盖原文后让旧认识看起来仍有依据。

## 增量与错误

衍生项目需要测试：分页中断、重复批次、修订重放、撤回/删除、凭证过期、范围被撤销、速率限制、来源字段变化。只有完整且同范围的快照才可能支持缺失对账；部分结果禁止做集合删除。

每类能力都应有 honest unsupported，而不是在无权限或 API 不存在时默默切到另一个数据来源。
